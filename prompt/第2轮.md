# 一、解除 Viewer Runtime 与 Demo Cube 的直接依赖

当前 `runtime.ts` 不应继续直接调用：

```ts

```

建立统一的模型输入 / 加载边界。

建议新增类似：

```text
src/models/
├── demoCube.ts
├── interactionTestModel.ts
├── types.ts
└── modelLoader.ts
```

具体文件名称可根据当前项目结构合理调整，但职责必须清晰。

Viewer Runtime 只接受统一的模型结果：

```ts
interface LoadedModel {
  root: THREE.Object3D

}
```

Runtime 不关心模型来源是：

```text
Demo Cube
测试模型
未来 GLB
人体
机器人
其他 Blender 模型
```

# 二、建立统一 ModelPart 类型

不要继续把：

```text
Three.js object.name
```

直接等同于长期业务 Part ID。

建立统一类型，例如：

```ts
interface ModelPart {
  id: string
  object: THREE.Object3D
  meshes: THREE.Mesh[]
}
```

如有必要可以增加：

```ts
sourceName?: string
```

但保持简洁。

职责定义：

```text
id
= 稳定业务部件 ID

object
= 部件根节点

meshes
= 该部件包含的所有可拾取 Mesh
```

Viewer：

```text
Raycaster
Highlight
Hover
Selected
```

统一基于 `ModelPart` 工作。

不要要求 `id === object.name`。

Demo Cube 可以暂时使用相同名称，但架构上必须解耦。

# 七、材质隔离规则

这是未来 Blender GLB 接入前必须验证的重点。

真实 GLB 中可能出现：

```text
多个 Mesh 共用同一个 Material
```

如果直接修改：

```ts
material.color
```

可能导致多个部位一起变色。

因此需要保证：

> Viewer 的 Highlight 操作不会意外修改其他 Part。

可以通过：

```text
需要高亮时 clone 材质
```

或其他合理方式解决。

但是：

- 不要每次 Hover 都创建新材质。
- 不要产生持续材质泄漏。
- clone 后的材质必须正确 dispose。
- 保持材质状态管理简单明确。

通过 `interactionTestModel` 验证该行为。
